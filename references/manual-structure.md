# Manual structure

Seven chapters work well for many software products; merge, rename, or omit a chapter when the product calls for it:

1. Purpose: what the product does, who uses it, and the expected input/output.
2. First use: installation, access, registration and prerequisites.
3. Interface or command map: where to find each main function.
4. Core workflow: real steps from input to completed result, including error states.
5. Outputs and interpretation: files, fields, units, formulas and limits that users must understand.
6. Data handling: local/cloud storage, backup, privacy, and routine maintenance if verified.
7. FAQ: observed or source-supported common failures and recovery actions.

Prioritize the highest-frequency workflow. Place a screenshot next to the step or state it explains, with a caption that identifies whether the content is an isolated UI capture or a synthetic demo result. A screenshot can supplement steps but cannot replace them. Do not add a fixed number of images or FAQ items to satisfy a template.

For bilingual content, each language must be complete on its own. Preserve product names, file names, units and algorithm identifiers; translate user-facing instructions and error explanations. If an image's UI language differs, label that difference in the caption. Review translated claims against the same source evidence, not just against each other.

For offline HTML, check desktop and phone widths. Keep figure captions next to images and make wide tables scroll without clipping nearby content.
